<decisions>
## Implementation Decisions

### Candidate Pool (FEAT-01)
- **D-01:** All 17 features from `build_features()` are candidates — no new features to engineer. They already cover 8 distinct regime dimensions with documented economic rationale (see features.py docstring).
- **D-02:** No always-in features — walk-forward CV decides everything, including whether VIX/VRP appear in the final set.

### Walk-Forward CV Design (FEAT-02)
- **D-03:** 3-year rolling train window / 1-year OOS test window. Step forward 1 year per fold. Gives ~11 folds over 2010–2026. Shorter than config.py WALK_FORWARD_TRAIN_YEARS=5 — chosen to capture regime-shift dynamics rather than over-smoothing with 5yr windows.
- **D-04:** Per-fold feature ranking: mutual information with regime label, computed on train fold data only. No model fitting required for the selection itself.
- **D-05:** Aggregation: a feature is included in the final set if selected in ≥60% of folds. No pre-targeted feature count — the 60% threshold determines the final size organically.

### Feature Selection Metric (FEAT-03)
- **D-06:** Primary metric: mutual information with regime label (sklearn.feature_selection.mutual_info_classif). Fast, model-free, causal (train-fold only).
- **D-07:** No fixed target size — let the 60% stability threshold decide. If 4 features pass, that's the answer. If 10 pass, that's also fine.

### Output & Integration (FEAT-03)
- **D-08:** After selection completes, FEATURE_SUBSET in config.py is updated automatically by the script. Old value preserved in a comment above the new assignment.
- **D-09:** Feature importance report: `data/feature_importance_report.md` — contains fold-selection frequency table (feature × fold), OOS MI score per feature, and short economic rationale note for each selected feature.
- **D-10:** Walk-forward selection script: `scripts/analysis/walk_forward_feature_selection.py` — consistent with Phase 4 pattern (analyze_regime_characterization.py lives there).

### Claude's Discretion
- Exact top-N cutoff per fold before applying the 60% aggregation threshold (e.g., top 8 per fold, or top 50th percentile by MI). Planner can choose a reasonable default.
- Whether to run a final validation pass after updating FEATURE_SUBSET (re-running diagnostics on the new feature set) — reasonable to include but user didn't specify.

</decisions>
